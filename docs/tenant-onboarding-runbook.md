# Tenant onboarding runbook

How to take a new institution from signed contract to students logging in.
Targets the §1.3 success criterion: **one institution, one branch, 10
classes and 500 students onboarded and usable within a day.**

Tenant = Frappe site (ADR-0001), so onboarding creates a real site with its
own database at `<subdomain>.<platform-domain>`.

## Why provisioning is not a button

Creating a site runs `bench new-site`, which needs database-root and
filesystem privileges. The application containers deliberately do not have
them. So the split is:

| Step | Where | Who |
|---|---|---|
| Register the tenant | Owner portal (web) | Platform owner |
| Create the site | Provisioning CLI on the bench host | Operator / deploy job |
| Onboard the roster | Tenant site (web) | Institution admin |

A compromised web session can therefore register a row, but cannot create,
suspend or destroy a site.

## 1. Register the tenant (owner portal)

Owner portal → Tenants → New, or via API:

```
POST /api/method/lms.lms.language_platform.api.register_tenant
{ "tenant_name": "Ankara Koleji", "subdomain": "ankara-koleji",
  "tenant_type": "Dershane", "plan": "Growth", "seat_limit": 500,
  "contact_email": "bt@ankarakoleji.edu.tr" }
```

The subdomain becomes a DNS label, a site directory and an argument to
`bench new-site`, so it is validated hard: lowercase DNS label only,
3–63 chars, no punycode, and not one of the reserved platform names
(`www`, `api`, `app`, `owner`, `vod`, …). Anything else is rejected
rather than repaired.

Status starts at **Requested**.

## 2. Provision the site (bench host)

Always dry-run first — it prints the exact commands without executing:

```bash
cd /home/frappe/frappe-bench
python apps/lms/provisioning/provision_tenant.py \
    --subdomain ankara-koleji \
    --base-domain dilplatformu.com \
    --control-site app.dilplatformu.com \
    --tenant-name "Ankara Koleji" \
    --admin-email bt@ankarakoleji.edu.tr \
    --dry-run
```

Drop `--dry-run` to run it. The CLI:

1. marks the tenant **Provisioning** in the registry,
2. creates the site (refusing to overwrite an existing one),
3. installs `frappe`, `payments`, `lms`,
4. applies tenant defaults and invites the institution admin as
   Moderator + Course Creator,
5. marks the tenant **Active**.

The site Administrator password is generated by the CLI and printed
**once**. Put it in the team password manager immediately — it is not
stored anywhere and cannot be recovered from the registry. The
institution admin never receives it: they activate through the invite
flow instead, so no credential travels through provisioning logs.

DNS needs no per-tenant work: the wildcard `*.dilplatformu.com` record
from the infra repo's `edge` module already resolves to CloudFront. Pass
`--dns-alias` only for premium tenants bringing a custom domain (§8.7).

## 3. Onboard the roster (tenant site)

Institution admin → import students from CSV:

| Column | Required | Notes |
|---|---|---|
| `email` | yes | becomes the login |
| `first_name` | yes | |
| `last_name` | no | |
| `class_name` | no | class is created on first sight |
| `student_id` | no | school's own number |
| `level` | no | CEFR A1–C2 |

Headers are case- and space-insensitive. Classes named in `class_name`
are created as LMS Batches automatically, which is how 10 classes and 500
students land from one file.

Import behaviour worth knowing before you run it on real data:

- **Duplicate emails within one file are rejected, not merged.** Two rows
  sharing an address usually means two different people were conflated;
  importing one silently would hide that.
- **Each row is isolated.** One bad record fails only itself and is
  reported with its spreadsheet row number, so a 500-row import never
  leaves you guessing which students landed.
- **The seat limit is enforced.** Check headroom first with
  `check_tenant_capacity`; an import that would exceed the plan is
  refused rather than partially applied.
- Uploads are capped at 2000 rows per request. Larger rosters should be
  split, or imported from the CLI where no HTTP timeout applies.

## 4. Verify

- [ ] `https://<subdomain>.<domain>` loads and the admin can log in
- [ ] Student count matches the roster; failures reviewed
- [ ] Classes appear with the right members
- [ ] A placement blueprint exists (create one, or copy a template)
- [ ] Retention windows reviewed with the institution (Ek-2 defaults:
      audio 30 d, transcripts 1 y, exam results 2 y)

## Suspension and reactivation

Suspension is two layers, and both matter:

```bash
# Registry: blocks further provisioning actions
POST /api/method/lms.lms.language_platform.api.suspend_tenant
{ "tenant": "ankara-koleji", "reason": "Non-payment, 60 days overdue" }

# Site: actually stops logins
python apps/lms/provisioning/provision_tenant.py \
    --action suspend --subdomain ankara-koleji --base-domain dilplatformu.com
```

Reactivate with `activate_tenant` and `--action resume`. Reasons are
mandatory on suspension and land in the audit trail.

The lifecycle refuses invalid jumps: a tenant cannot go from Requested
straight to Active without provisioning having run, and Archived is
terminal.

## Not automated yet

- **Archival/offboarding**: `bench drop-site` plus data export is
  deliberately manual — it is destructive and irreversible.
- **Seat sync**: `active_students` on the registry is updated by the
  provisioning tooling, not live from each tenant site. Treat it as
  indicative between syncs.
- **Per-tenant AWS resources** (dedicated buckets, custom domains) are
  Enterprise-package work and are provisioned from the infra repo.
